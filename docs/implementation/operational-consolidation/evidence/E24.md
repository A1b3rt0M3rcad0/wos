# E24 — Canonical credential authority in lease commands

- Baseline: E23 at `bb7ef9b`.
- Implementation: `d525856`.
- Scope: resolve the presented credential and its canonical root, then apply that ownership consistently to claim, renew, reclaim, release, completion and capability projections.
- Behavior: the resolver validates credential ID, namespace, Principal, Actor, parent chain, expiration and revocation inside the command transaction. The root credential identifies lease ownership; authorization remains based on the presented session credential and its effective permissions. Capabilities distinguish own, other, expired and legacy-unbound leases. Reclaim of an expired legacy lease is an explicit adoption into a bound lease.
- Validation: application and domain focused credential-authority tests passed; the full domain, application, Memory, SQLite, PostgreSQL, HTTP and MCP package suites passed with a live PostgreSQL service. `go vet` passed on the same packages.
- Limits: an embedded host that cannot provide a trusted credential identity retains compatibility only for unbound legacy operations. Credential-bound receipt replay is handled by E25.
- State: **verified**.
