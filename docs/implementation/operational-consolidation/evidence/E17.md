# E17 — Migrate legacy permissions without granting future powers

Implemented in commit `9099f9bf008287697062edce5eb9ee174216e8c5` on `fix/workspace-operational-density`. E17's SQLite migration is `0038_permission_compatibility.sql`; PostgreSQL's generated counterpart has the same version. This preserves monotonic migration ordering after `0037_operational_profile.sql`; later planned migrations are renumbered in the migration allocation map.

The implementation adds a frozen `legacy-v1` crosswalk keyed by exact command and granular permission, a read-only application preview, and an internal apply method requiring `permissions:manage`, an audit reason, an idempotency key, and expected Namespace and optional CredentialPolicy revisions. Apply changes only the compatibility markers, the policy revision when a policy exists, the Namespace revision, an audit row, and its replay receipt in one storage transaction. It does not publish a migration operation through HTTP, MCP, CLI, or the capability catalogue. Ordinary grant and CredentialPolicy writes cannot forge a marker. Existing `planning:write` remains the exact primary right for `CreatePlanItems`; its Objective/criterion and Task side effects retain their pre-granular `outcome:write` and `work:write` requirements.

The reviewable crosswalk and rollout semantics are documented in [`permission-map.md`](../permission-map.md). Tests compare the unmigrated and migrated authority, prove the exact mapped Task creation permission becomes usable only after both grant and policy markers are applied, and cover preview immutability, CAS conflicts, replay, empty grants, and revocation races.
