# E20 — Credential lifecycle management

- Baseline/head before: `2425c0f` (E19 evidence commit).
- Implementation commit: `2d5adb6cee625ce0bd41cbeb232515895a3fc60b`.
- Scope: safe credential list/detail, metadata and policy updates, explicit rotation overlap/provenance, last-used observation, Memory/SQLite/generated PostgreSQL parity, HTTP and MCP operations.
- Behavior implemented: administrators can page through root credentials and inspect metadata plus the effective policy (frozen credential policy intersected with the Principal's current grant). Responses omit credential digests and bearer tokens. Queries support bounded page size, cursor and principal/status/actor filters.
- Update behavior: name, description, expiration and optional frozen policy are protected by expected Namespace, metadata and policy revisions. The target Principal's current Namespace grant and policy scope are checked again within the storage transaction. Policy updates cannot add permissions outside that grant.
- Rotation behavior: a new credential is issued to the same Principal and Actor, with no policy expansion. The old credential remains valid only through the caller-selected overlap, and then expires. Both records retain replacement provenance. Rotation does not change or transfer any work lease. The replacement token is returned only on the initial response; a matching receipt replay returns safe metadata with the token omitted.
- Usage observation: successful authentication makes a best-effort update of the canonical root credential's `last_used_at`. Adapters coalesce writes to one per five-minute window; telemetry errors do not fail authentication.
- Migration: additive `0040_credential_lifecycle.sql`; latest schema version is 40. PostgreSQL migration and adapter/test sources are generated from the SQLite source. The generator is stable on a second run.

- Compatibility and limits: legacy credentials without lifecycle metadata cannot be edited or rotated through this path; they can be replaced by issuing a new credential. Read authorization for management queries is revalidated in the subsequent E21 hardening stage. No lease is assigned to the replacement credential by this rotation operation.
