# WOS 0.3.0

- Add opt-in signed contract protocol v2, protected actor profiles, independent review and correction, receipt-driven cleanup and historical upgrade/restore; align five portable skills and the human workspace, and separate coordinated verification from explicit registry publication.

Packages: WOS service with wosctl and five portable skills. Service target: Linux amd64. Client assets: Linux amd64 and Windows amd64; actual matching native test receipts are required before publication. Skills require Node >=22 and a compatible runtime. Cross-building and release preparation do not certify Windows or registry publication.

## Upgrade and operation

Back up the existing SQL database and preserve immutable issued material, drafts
and receipts before upgrading. Actual v0.2.0 fixture/backup/restore verification
checks schema 19 to 26 without manufacturing signatures for unsigned history.
Retire old writers, explicitly drain the Namespace, then activate signed v2;
existing Namespaces retain their recorded phase. Runtime readiness checks
persistent schema, live signed Namespace requirements and the pinned issuer.
An old executable may bind its port but must fail readiness against future
schemas. Do not use port binding alone as upgrade evidence.

Workspace schema 2 uses project.yaml and separate profiles/<name>/profile.yaml
and contract/ directories. Use protected key references and authorized enrollment;
never copy credential/private key values into a task prompt. Inspect migration
with its bounded dry run, then explicitly convert legacy local data into a
separate workspace. Existing unsigned material is never silently re-signed.

Read the bounded issued specification, execute only its obligation and return
with the original signed intent. Delivery for review closes the executor's local
obligation; Task DONE requires the independent assessment. A correction acquires
a fresh contract with --previous-review acknowledging the frozen case. Recovery
uses the original command, credential identity and exact receipt rather than
creating another acquisition or submission.

## Evidence and limits

Hosted native Linux/Windows protected-key, process-lock and HTTP/CLI gates are
implemented. Publication requires their actual receipts for this final source
and matching archive hashes, plus core SQL/race, browser and offline package
acceptance. Preparation of this version is not proof those final-source gates
have completed. Coordinated verification uploads reviewable artifacts; npm,
GHCR and GitHub publication requires explicit workflow_dispatch publish=true.
No external registry publication is claimed by these notes.

The managed Codex pilot used fresh executor/reviewer task contexts and completed
a real implementation with independent tests and receipt cleanup. The installed
package journey additionally exercises changes_requested and correction. Shared
filesystems are not OS privilege isolation; a portable skill guides delegation
but does not supply a scheduler, isolated model context or universal runtime
certification. Claude, Hermes, OpenClaw and Woobe execution remain distinct
consumer validation, even though installer destinations are verified.

Signed workload/fuzz/SQL failure and recovery gates retain actual measurements
and limits. Bounded historical density and shared-Outcome contention are not a
production SLA. Controlled A/B/C context/cost reporting preserves unknown usage;
A/B/C functional comparators were executed with one task each and the same 43
external checks. Provider billing/token telemetry remains unavailable. Fixed
ordering, parent orchestration and C bug diagnosis preclude a performance or
savings claim; see docs/audit/controlled-codex-2026-10-09.
