## Concurrency and delivery limits

SQLite remains an embedded single-writer backend, not a multiwriter service. PostgreSQL is the shared/replica backend, but Namespace/security serialization and exact retries still limit throughput. The complete source-bound [12-case matrix](../audit/operational-hardening-2026-10-15/qualification/contention-6e91208/) covers 1/4 active Outcomes x 2/8/50 consumers and requires one version-collision winner, explicit independent approval, exactly retained original intentions on conflict and stable outbox identities. It is not a count of supported users or sessions. At 50 consumers the complete 6e91208 matrix measures SQLite p95 about 4.06–4.18 seconds and PostgreSQL 91.42–140.45 seconds, with about 5,000 conflicts/exact retries on PostgreSQL. These cases exhibit substantial guard contention; do not claim PostgreSQL is invariably faster or sell these measurements as production capacity. Size a deployment with its own representative load and explicit latency/queue objectives.

Delivery's test objectives are complete authoritative ACKs within the declared fixture timeout, stale-fence refusal, bounded lanes and durable external dedupe after interrupted ACK/restore. External duplicates are expected: 100 events may cause more than 100 receiver requests, while a durable consumer ledger retains 100 effects. Four PostgreSQL lanes are a measured starting reference, default remains one. SQLite above one lane does not add writers. A failed worker is observable while the API may remain ready; an external supervisor/monitor decides when to restart that process.

## Operator obligations and remaining certification

The backup tools and cron/systemd/Kubernetes examples are opt-in and do not install a scheduler. Backup age, independently validated restore age, queue age/exhaustion, database/volume quota, history growth and pool contention must be collected and alerted externally. Keep protected issuer/agent keys and CLI drafts/journal/pending receipts separately; never clear a pending intention because of a timeout. Restore does not extend leases, undo external effects or recover security changes made after the snapshot. Fixture RTO/RPO reports state their exact measurement boundary and do not establish hosting guarantees.

Upgrade requires a coordinated cutover: pause mutations and stop all old API/worker processes before migrating, then start only replicas of the same qualified source. Mixed old/new server rolling upgrades are outside this envelope; an old binary's startup refusal does not fence an already running process. Follow the [explicit cutover procedure](../operations.md#upgrade-cutover-for-the-operational-candidate) before enabling new-schema behavior.

The actual 0.4.2 upgrade preserves original rows in 67 tables, verifies 39 old DSSE facts with current codec/public keys, and rejects the old binary on schema 29. The [downloaded published Linux asset](../audit/operational-hardening-2026-10-15/qualification/actual-released-v042-refusal.json), checked against the published SHA256SUMS, also refuses schema 29 without changing logical records. Configured missing private seed fails explicitly rather than substituting an issuer. Reverse execution of the new resolution feature by an old strict CLI is not promised; use the updated CLI for a new-feature pending resolution. Old workspace 1/2, v1 unsigned history and existing accepted receipts retain separate regression gates.

Human comprehension/usability testing and manual screen-reader/zoom validation remain pending under the owner's explicit prior instruction. Automated browser/native success does not replace that work. Production percentiles/SLA, thousands of signed writers, external billing/token costs and deployment-specific secret/OS isolation are not certified here. WOS 1.0 remains unqualified/unpublished. PR #106 must stay open without merge/publication until the owner separately authorizes integration.
